em paralelo ao treino neste repositório. Serve para quem pegar o rodízio pela primeira vez saber
**o que esperar de um dia real** e **o que já foi aprendido na prática**.

## 2. O treino neste repositório (24/09, à tarde)

Todos os exercícios da quinta foram feitos **pela tela do GitHub**:

| Exercício | O que se aprendeu |
|---|---|
| 1. *Resolve conversation* | botão cinza com aprovação em ordem = conversa aberta. `blocked` → `clean` depois do clique |
| 2. *Resolve conflicts* (CHANGELOG) | manter os dois lados, apagar só os 3 marcadores. O commit vai para a branch **do card** |
| 3. Corte | mergear uma por vez olhando a caixa de merge; não apagar a branch; o `.sql` entra sem aviso |
| 4. Backmerge `master → develop` | botão *Resolve conflicts* **desabilitado** → branch intermediária no terminal → fechar a PR morta → PR nova com a intermediária no *compare* → provar `develop...master = 0` |
| 5. PR `develop → homolog` | ler o Actions: `build_push` e `deploy_homolog` verdes, os outros três `skipped` |
| 6. Lista para o suporte | hotfix já em produção fica fora; card que depende de script vai com aviso |

**O erro mais comum do dia:** criar a PR e achar que acabou. No Exercício 4 a PR foi criada certa,
mas o merge ainda não tinha sido feito, e o compare continuava em 2. **Medir no fim** é o que pega isso.

## 3. A quinta real, hora a hora

### 08:40 — Passo 1: a casa está arrumada?

O deploy da semana anterior tinha fechado nos dois repos (tag publicada, jobs verdes,
`develop...<PROD> = 0`). Mas `develop...homolog` dava **9** num repo e **1** no outro.

**Não era problema:** eram só commits de merge das releases anteriores, com **0 arquivos de
diferença**. A simulação do merge da noite deu limpa. Lição: **olhe o diff de conteúdo, não só a
contagem de commits.**

### 08:42 — 1º toque

24 PRs abertas, **só 2 prontas**. O gargalo não era aprovação:

| Pendência | Quantas PRs |
|---|---|
| conversas de review sem *Resolve conversation* | ~20 |
| conflito (em **todas** as 12, o CHANGELOG estava entre os arquivos) | 12 |
| conflito em código (volta para o dono) | 5 |
| mudanças pedidas | 8 |

Mensagem no canal de PRs com a lista inteira + uma DM por dono, com a pendência de cada PR.

### Manhã — a dúvida sobre a aprovação

Surgiu a hipótese: *"resolver só o CHANGELOG não derruba a aprovação, porque não mexe no código do
autor"*. **Foi verificado nas PRs reais, e derruba.** Numa PR, o único commit depois da aprovação
foi um merge que resolveu **só** o CHANGELOG, e a aprovação caiu no mesmo minuto do push. Em outra,
caíram as duas aprovações.

**Por quê:** para o GitHub, o CHANGELOG é arquivo do autor (ele escreveu uma entrada lá, por isso
conflitou). Resolver muda o diff da PR, e isso dispara o `dismiss_stale_reviews_on_push`.

### 12:00 — o efeito cascata do CHANGELOG

Uma PR entrou às 09:56, e as **duas que estavam prontas passaram a conflitar** no CHANGELOG. Uma
resolução preparada ao meio-dia ficou velha às 14h, porque entraram mais três PRs.

Daí veio a regra do dia:

> **Conflito de CHANGELOG: avisa o dono. Se às ~17h a PR estiver aprovada, sem conversa aberta e
> presa só por isso, quem está no rodízio resolve — uma PR por vez, com o revisor re-aprovando
> entre uma e outra.**

### 14:14 — 2º toque

Tudo recalculado, e muita coisa tinha mudado:

- 4 PRs entraram na develop
- uma PR ganhou **conflito em código** que de manhã não tinha (outra PR que entrou mexeu no mesmo relatório)
- 2 PRs novas foram abertas
- **um hotfix foi direto para a produção** em um dos repos, e a develop ficou 2 commits atrás.
  Backmerge simulado: limpo, e sem esbarrar na PR aberta que mexe no mesmo arquivo. Fica para
  depois do corte, antes da homolog.
- **"Changes requested" que não sai:** duas PRs tinham a aprovação de um revisor, mas seguiam
  bloqueadas porque outros dois tinham pedido mudança. Só quem pediu retira.

Resposta na thread da manhã + DM só para quem ainda tinha pendência, dizendo **de quem** dependia
cada uma.

## 4. As lições, em uma lista

1. **Recalcule a cada toque.** Em 5 horas o quadro mudou por completo.
2. **O gargalo costuma ser conversa aberta, não aprovação.** Diga isso com todas as letras na cobrança.
3. **O push derruba a aprovação mesmo resolvendo só o CHANGELOG.** Combine o revisor antes.
4. **Resolver CHANGELOG cedo é retrabalho.** Cada merge recria o conflito em todas as outras PRs.
5. **Contagem de commits engana.** `ahead_by` > 0 com 0 arquivos de diferença = só commits de merge.
6. **Hotfix direto em produção acontece no meio da quinta.** Refaça os compares depois do corte.
7. **"Changes requested" só sai com re-review de quem pediu.**
8. **Scripts de banco entram em silêncio.** Varra os arquivos das PRs que entraram, a cada rodada.
9. **Não apague branch de ninguém** depois do merge.
10. **"Eu fiz" não é evidência.** Termine cada etapa com o número que prova (`ahead_by = 0`).
